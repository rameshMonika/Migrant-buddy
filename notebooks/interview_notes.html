Interview Notes · Project Deep-Dive

migrantBuddy

A retrieval-augmented assistant that answers Singapore migrant workers' questions — salary, working hours, permit conditions, medical insurance, help & contact info — grounded in official MOM guidance, in the worker's own language.

Stack FastAPI + LangGraph · Next.js · Chroma · Redis · Ollama/vLLM Status full stack running, dockerized Languages EN + 7 SEA-LION languages
01

What it does

A migrant worker asks a question — by text, or by speaking into the browser — in English, Tamil, Burmese, Thai, Vietnamese, Malay, Filipino or Indonesian. The system retrieves the relevant passage from MOM's official guidance, and answers in the language the question was asked in, with an optional talking-avatar readback for workers who find spoken answers easier to trust or follow than text.

The corpus is intentionally narrow and real: five MOM source pages across salary, working hours, work-permit conditions, medical insurance, and help/contact info — chosen over a broader scrape because three other candidate categories (employment rights, work injury/WICA, housing) turned out to be navigation-only landing pages with no real content on the sourced URL, and were dropped rather than ingested as near-empty stubs.

The core design bet: a multilingual embedding model (BGE-M3) can retrieve directly against non-English queries without a translation step, and a SEA-LION-tuned generation model can answer natively in that language off English-source context — so translation never becomes a separate pipeline stage on either side of the request.
02

System architecture

Eight containers, one Docker Compose stack: four services the team owns (frontend, rag, speech, tts), three backing stores/model runtimes (Chroma embedded in-process, Redis, Ollama, vLLM), and two third-party APIs reached over the open internet. Every internal hop is plain HTTP/WS on the compose network's DNS (service name as hostname); every browser-facing hop goes through a published host port, and two of those host ports were reassigned because something else on the dev machine already held :8000 and :3000.

Why four services, not one monolith

  • rag is latency-critical (streams tokens) and CPU/GPU-bound on embedding + generation — kept lean, no audio dependencies dragging its image size or cold-start up.
  • speech pulls in faster-whisper and a large model cache (its own named volume, whisper-hf-cache) that's independent of RAG's lifecycle — restarted/scaled without touching chat.
  • tts is two thin outbound HTTP clients (ElevenLabs, LiveAvatar) with no local model — stays a lightweight, fast-building container.
  • Each ships as its own Docker build target from one shared Dockerfile, and its own pushable image (migrantbuddy-rag, -speech, -tts, -frontend) for independent deploys.
  • Host ports 8000 and 3000 collided with unrelated containers already running on the dev box (a Prometheus exporter, a Grafana instance) — republished on 8010/3001. The container-internal ports (8000, 3000) are untouched; only the host side moved, which is why the frontend's build-time NEXT_PUBLIC_* URLs point at :8010, not :8000.

Ingestion — fetch, extract, validate

Five MOM source URLs, each hand-tagged with a category (salary, working-hours, work-permit, medical, help) via a SourceSpec — deliberately not a corpus-wide crawl. Per source:

Fetch & cache raw HTML

Plain requests.get with a declared User-Agent, then the untouched HTML is written to disk before any parsing (cache_raw_html). Only 5 pages, so no concurrency or rate-limiting — but caching first means extraction can be re-run and debugged offline without re-hitting mom.gov.sg.

Extract to markdown

trafilatura.extract(html, output_format="markdown", include_tables=True, include_comments=False, favor_precision=False) — strips nav/footer/boilerplate but keeps tables inline, correctly positioned relative to their surrounding headings. favor_precision=False is deliberate: trafilatura's precision mode trims aggressively and risks cutting real MOM guidance text along with boilerplate; recall matters more here than a slightly noisier extraction.

Assemble the record

build_document pulls title/metadata via trafilatura.extract_metadata and stamps a stable document_id (a slugified URL), authority="MOM", the per-source category, the constant content_type="official_guidance", and language="en" — the corpus itself is monolingual English; multilinguality lives entirely on the query side (embedding + generation), not in the source documents.

Validate before trusting it

validate_documents hard-fails on a missing title, empty text, or text under 500 characters (catches a page reduced to near-nothing after boilerplate stripping) — this is exactly how the WICA and housing pages got caught and dropped, since both extracted down to almost pure navigation. A missing heading structure only warns — a short, heading-less contact page can be legitimate.

Chunking — structure-aware, five deterministic passes

Pure text transformation, no I/O or model loading, so it's cheap to unit-test in isolation from embedding. Token counting is a heuristic, not a real tokenizer — len(text) // 4 — accurate enough to budget chunk sizes without pulling in a tokenizer dependency for a text-splitting step that doesn't need exact counts. Target: 300–500 tokens, 15–20% overlap, tuned against a naive fixed-window baseline across 300/500/800-token and 10%/20%-overlap variants.

Split on headings — split_by_headers

Regex-matches ##/### lines (tolerant of stray leading whitespace some pages picked up from trafilatura extraction) and walks them with a level-aware stack, so each section keeps a full breadcrumb like "Overtime pay > How overtime pay is calculated", not just its immediate heading.

Merge undersized sections — merge_sections

Heading-splitting alone leaves plenty of sections far smaller than the 300-token floor. Adjacent sections are merged forward, greedily, until adding the next one would exceed chunk_size — trading a few merged/less-precise heading paths for chunks that are actually retrieval-sized.

Protect tables, then split oversized sections — split_oversized

Any section still over budget is recursively split at paragraph boundaries with overlap (pack_blocks: greedy bin-packing, carrying the trailing ~15–20% of blocks forward into the next chunk for continuity). Before that split runs, every markdown table block is swapped out for a placeholder token (protect_tables) so the paragraph splitter can never land inside one — the placeholder is restored after packing, so a table only ever counts against its chunk's token budget as a single atomic block, even if that pushes the chunk over the nominal size cap.

Prefix a breadcrumb — add_breadcrumb

Every chunk's text is prefixed with "{document title} > {heading path}" before embedding. A chunk retrieved on its own — with no surrounding page context — still carries enough of the document structure to be understood and correctly attributed.

Validate the invariant — validate_chunks

A correctness guard, not a stylistic check: counts table blocks in the source document and sums table blocks across that document's resulting chunks — if they don't match, a table was split, and the run raises rather than silently shipping a broken chunk.

Each chunk keeps chunk_id, document_id, url, heading_path, and token_count alongside the text — enough to trace any retrieved chunk back to its exact source section for citation.

Embedding — BGE-M3 settled

BAAI/bge-m3, 1024-dim, multilingual. Chosen specifically so queries in Tamil, Burmese, Thai etc. retrieve directly against the English-source corpus with no pre-retrieval translation step. Compared against a 384-dim paraphrase-multilingual-MiniLM-L12-v2 variant (its own Chroma collection — dimensions aren't shareable) as the lighter-weight alternative.

Retrieval — hybrid BM25 + dense, then rerank settled

Chroma indexes BGE-M3 dense vectors; BM25 runs lexical scoring in parallel; results are combined (hybrid) and passed through a reranker. Five retrieval strategies were run head-to-head on a 10-query labeled set (7 non-English, 16-chunk corpus, k=3) — see results below. The winner: hybrid retrieval reranked with SEA-LION-E5, not dense alone and not hybrid unreranked.

Open question, not yet resolved: BM25's lexical overlap mostly disappears for non-English queries against an English corpus (aside from proper nouns like "S Pass" or dollar figures) — worth splitting hybrid-vs-dense-only by query language rather than assuming BM25 helps uniformly across all of them.

Deferred, not built: query rewriting + dual retrieval (retrieve on both the original and an English-translated query, then merge) as a targeted fix for that BM25 weakness — parked until real user query examples exist to confirm it's an actual problem, not a speculative one.

Generation — SEA-LION 8B settled

aisingapore/Llama-SEA-LION-v3-8B-IT, chosen over qwen3:8b at the same parameter class specifically to isolate language specialization from model size. Generates directly in the query's language — confirmed by a 10-query smoke test (7 non-English) with no "answer in the query's language" instruction in the system prompt; it answered natively every time anyway.

Conversation memory — LangGraph live

Multi-turn state lives server-side, keyed by thread_id — the frontend only ever sends {message, thread_id}, never full history. A compiled StateGraph runs four nodes per turn:

  • summarize — no-op until conversation length crosses a threshold, then condenses older turns instead of growing the prompt unboundedly.
  • rewrite_query — folds history + the latest message into a standalone retrieval query. A bare follow-up like "what about for daily-rated workers?" has almost no signal for the retriever on its own.
  • retrieve — the same hybrid + SEA-LION-E5 rerank path above, optionally hitting a Redis-backed retrieval cache first.
  • generate — the graph is compiled with interrupt_before=["generate"]: the graph pauses right before this node so /chat can stream the answer token-by-token from outside the graph, then write the finished text back in and resume to END. A deliberate two-phase invoke — not a single blocking call — purely to make streaming and checkpointing compatible.

Checkpointer backend is env-switchable: memory (LangGraph's in-memory saver, default, lost on restart) or redis (thread_id-keyed, TTL-expiring). The Redis branch is written and wired but not yet verified against a live instance — flagged as the most likely spot for an API-shape mismatch once Memurai is actually running locally.

04

Evaluation & results

Every retrieval or prompt change that graduates out of a notebook carries a Ragas run showing it didn't regress. Retrieval is scored on precision/recall/MRR against a labeled (query, relevant-doc) set; generation on faithfulness (groundedness to retrieved context) and answer relevancy, judged by llama3.1:8b.

Metric glossary — what each one measures, how it's computed

MetricWhat it measuresHow it's measured
Hit@3Whether the one correct chunk shows up anywhere in the top 3 results — a pure yes/no on retrieval reach.1 if correct_chunk_id ∈ top-3 ranked IDs, else 0; averaged over all 10 queries.
Precision@3What fraction of the top-3 slots were actually relevant — in principle, how "wasteful" the top-k is.(# relevant in top-3) / 3. With exactly 1 relevant chunk per query here, this collapses to hit@3 / 3 — capped at 0.333 even under perfect retrieval, see note above.
Recall@3What fraction of all relevant chunks for the query were retrieved in the top 3.(# relevant in top-3) / (total relevant). Total relevant = 1 here, so this is identical to hit@3 in every row — not an independent signal in this eval design.
MRRHow near the top (not just "in top-3") the correct chunk lands — rewards rank 1 much more than rank 3.1 / rank if found (0 if missed), averaged over all 10 queries. A miss anywhere counts as a hard 0, not a partial credit.
nDCG@3Same rank-position sensitivity as MRR, but normalized to a 0–1 scale against the best-possible ordering.Discounted gain 1 / log₂(rank + 1) for the correct chunk if within top-3, divided by the ideal DCG (correct chunk at rank 1).
LatencyWall-clock cost of one query's retrieval (embedding + search + fusion + rerank, whichever apply).Averaged per-query time across the 10-query run, on whatever device the notebook executed on (not pinned to CPU/GPU in the findings).
Faithfulness RagasWhether the generated answer is actually grounded in the retrieved context — the core anti-hallucination check.Ragas breaks the answer into individual claims, then asks the judge LLM (llama3.1:8b) to verify each claim against the retrieved chunks; score = fraction of claims that are supported.
Answer Relevancy RagasWhether the answer actually addresses the question asked — independent of whether it's grounded.Ragas has the judge LLM generate several plausible questions the answer could be answering, embeds them, and scores cosine similarity back to the original query — a low score means the answer drifted off-topic even if every claim in it was true.

Faithfulness and Answer Relevancy are deliberately independent axes: an answer can be perfectly grounded but off-topic (high faithfulness, low relevancy), or on-topic but making things up (low faithfulness, high relevancy). Tracking both separately is why the SEA-LION vs qwen3 comparison could isolate a faithfulness-specific win rather than a vaguer "better answers" claim.

Hit@3/recall@3 alone don't separate the top two — bge-reranker-v2-m3 ties SEA-LION-E5 at a perfect 1.000 on both. The gap shows up in where the right chunk lands inside the top 3: MRR (0.817 vs 0.950) and nDCG@3 (0.863 vs 0.963) both reward ranking it 1st over 3rd, and SEA-LION-E5 does that more consistently. Latency between the two rerankers is a wash (4772ms vs 4872ms) — the win is rank quality, not speed.

Why the numbers land exactly there

The eval set is built with exactly one labeled-relevant chunk per query (each entry has a single correct_chunk_id, asserted unique at build time) — that one design choice pins down most of the arithmetic in the table:

  • recall@3 = hits / len(relevant_ids) = hits / 1 — so recall@3 is always identical to hit@3, row for row. There's nothing recall@3 is telling you here that hit@3 isn't; with one relevant item, "found it" and "found all of it" are the same event.
  • precision@3 = hits / 3, hits ∈ {0,1} — so precision@3 is always exactly hit@3 ÷ 3: 0.900→0.300, 0.600→0.200, 1.000→0.333. It isn't measuring a distinct quality either; it's a fixed rescaling forced by k=3 and a single relevant chunk. With this eval design, precision@3 and recall@3 are redundant with hit@3 — MRR and nDCG@3 are where the real signal is, because they're rank-position-sensitive.
MRR = average of 1 / rank_of_correct_chunk (0 if missed entirely) — rewards the correct chunk being first, heavily penalizes it being 2nd or 3rd, and zeroes out a miss.
nDCG@3 = discounted-gain of the correct chunk's position (weighted 1/log₂(rank+1)), normalized against the best-possible ordering — same rank-sensitivity as MRR, on a 0–1 scale.
Hybrid fusion is Reciprocal Rank Fusion (constant 60) over the top-10 dense and top-10 BM25 candidate lists: score[chunk] += 1/(60 + rank) — every method reranks the same fused candidate pool, not a fresh retrieval.

Row by row

BM25 only — 0.403 MRR, 0.600 hit@3

Misses the correct chunk in top-3 on 4 of 10 queries outright — almost all non-English, where lexical term overlap against the English-source corpus barely exists. The 6 it does hit average well below rank 1, dragging MRR down further.

hybrid_rerank + ms-marco — 0.425 MRR, worse than no rerank

An English-only cross-encoder rescoring a candidate pool that's already 70% non-English queries: it actively demotes correct chunks RRF had already surfaced, because it's scoring surface lexical match it can't compute meaningfully in Tamil/Burmese/Thai/etc. Reranking with the wrong model is worse than not reranking at all.

hybrid (no rerank) — 0.783 MRR vs dense's 0.875, same 0.900 hit@3

Fusing in a weak BM25 signal doesn't push the correct chunk out of the top 3 (hit@3 unchanged) — it dilutes dense's already-strong ordering within the top 3, bumping the right chunk from 1st to 2nd/3rd often enough to cost 0.09 MRR. BM25's own signal is noisy on non-English queries, so mixing it in adds noise to a top-1 position dense was already getting mostly right.

dense only — 0.875 MRR, 0.900 hit@3

BGE-M3's multilingual embeddings alone are a strong baseline precisely because they don't depend on lexical overlap at all — 1 of 10 queries still misses the top-3 entirely, which is the ceiling a reranker then has to lift.

bge-reranker-v2-m3 / SEA-LION-E5 — both reach 1.000 hit@3

Both multilingual rerankers recover dense's one miss, pushing every query's correct chunk into the top 3. SEA-LION-E5's extra edge (0.950 vs 0.817 MRR) is entirely about where inside the top 3 — it lands the correct chunk at rank 1 more consistently, which is exactly the SEA-LION-tuned reranker's job on this SEA-language-heavy query set.

Two numbers in this table are honestly unexplained, not swept under the rug: hybrid (no rerank) clocks 55ms — faster than dense alone at 137ms — despite hybrid_retrieve literally calling dense retrieval plus BM25 plus RRF fusion, strictly more work. The likely cause is measurement order (dense runs first in the benchmark loop and probably absorbs a one-time model warm-up cost later methods don't pay), but that's an inference, not something the notebook states. Similarly, SEA-LION-E5 is noted as a bi-encoder while bge-reranker-v2-m3 is a true cross-encoder, yet both cost ~4.8s — architecture alone doesn't explain why they're latency-matched while ms-marco-MiniLM (267ms) is ~18× faster than either. Worth saying "I don't know, here's my best guess" on both if asked, rather than inventing a clean story.

Why two queries got dropped — the judge, not the model, was the problem

Burmese: 1.0 → 0.25

Run A (qwen3, dense) scored perfect faithfulness; Run B (same model, different retrieval) scored 0.25 on the identical query. Traced to qwen3 generation randomness, not a retrieval regression — the retrieved context was fine in both runs.

Thai: 0.0 in every run

Scored zero regardless of model or retrieval strategy — a judge limitation. llama3.1:8b struggles to verify Thai-language answers against English-source context, not evidence the answer was actually wrong.

Both were excluded from the 8-query comparison runs so the generation-model comparison wasn't swamped by judge noise unrelated to what was being tested.

05

Speech, TTS & avatar

Two supporting services, each a thin, focused layer — neither trains or hosts a model itself except Whisper, which is local.

speech — real-time transcription

Wraps faster-whisper behind a WebSocket (/transcribe/ws) so audio streams in and partial/final transcripts stream back, rather than a single record-then-upload round trip. Multilingual with auto language detection — no separate language toggle needed in the UI, matching the "no translation stage" philosophy of the RAG pipeline itself. Runs as its own container so the Whisper model cache (mounted as a named volume) isn't tied to the RAG service's lifecycle.

tts — voice & talking avatar

Two independent outbound integrations behind one service:

  • ElevenLabs — text-to-speech for a plain audio readback of the answer.
  • LiveAvatar (HeyGen) — /session/start mints a short-lived WebRTC session token server-side (the only step needing the secret API key); the frontend uses that token to open the avatar session and call repeatAudio() directly, client-side, without ever touching the real API key.

The security shape here is worth stating explicitly if asked: secrets never leave the server; the browser only ever holds a short-lived, scoped session token.

06

Infra & serving

Generation backend — env-switchable

Ollama for local dev iteration; vLLM for production (continuous batching / PagedAttention throughput). vLLM now runs with on-the-fly 4-bit bitsandbytes quantization — fits an 8GB-VRAM box where full bf16 didn't.

Streaming — SSE, hand-rolled

/chat returns sources once retrieval finishes, then repeated token events, then done. No new dependency — considered too simple to justify one.

Retrieval cache

Redis-backed, TTL'd (86 400s in compose), toggled independently of the LangGraph checkpointer backend — you may want caching without persistent conversations, or vice versa.

Rate limiting

Only /chat is limited, keyed by client host; a denied request 429s before the stream opens, not mid-stream. /health is intentionally exempt and dependency-free, so liveness checks don't flap when Ollama is briefly down.

Docker Compose

docker-compose.vllm.yml is included from the main compose file — kept separate to iterate on/debug vLLM in isolation, but docker compose up still brings up the full stack in one command.

Observability

Langfuse wired in for LLM call tracing across the RAG graph's multiple LLM hops (rewrite, generate) — useful for debugging exactly which node produced a bad answer in a multi-turn conversation.

07

Likely interview questions

Why hybrid retrieval if dense-only (0.875 MRR) beat hybrid unreranked (0.783)?
Because reranking recovers it — hybrid+SEA-LION-E5 (0.950) beats dense alone. The unreranked hybrid number shows BM25 dilutes results on its own; the fix wasn't dropping BM25, it was adding a reranker strong enough to filter what BM25's noise let through.
Why not just always translate to English first?
Two reasons tested directly: BGE-M3 retrieves competitively against native-language queries without it, and SEA-LION generates natively in-language off English context without being told to. Adding translation would be an extra LLM hop solving a problem the evals didn't show existed — it's parked as a deferred fix specifically for BM25's non-English weakness, not adopted wholesale.
Why does /chat interrupt the LangGraph graph before generate instead of just calling it?
Streaming and LangGraph checkpointing don't compose for free — invoking straight through would only yield the graph's final state, not token deltas. Pausing before generate, streaming from outside the graph, then writing the result back in and resuming to END keeps checkpointing (for multi-turn memory) and token-level streaming (for time-to-first-token) both intact, at the cost of every caller — including tests — needing to follow that two-phase pattern instead of one plain invoke().
Is the SEA-LION generation win statistically solid?
No, and worth saying so unprompted — it's an 8-query eval set. The Burmese/Thai episode (a qwen3 randomness artifact and a judge-language limitation, respectively) shows how much one query flip can move these averages. The +0.106 faithfulness gap is a real, direction-consistent signal, not proof at scale.
What's still genuinely unverified end-to-end?
The Redis-backed LangGraph checkpointer — written against the expected langgraph-checkpoint-redis API shape but never run against a live Redis/Memurai instance, so the TTL parameter shape in particular is flagged as the likely first thing to break.
